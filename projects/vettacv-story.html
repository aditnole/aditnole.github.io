Building VettaCV: from a tailoring script to a production job-search app

VettaCV started as a side project with one idea: a resume should be rewritten for every job you apply to. Two and a half years later it parses resumes, tailors them, matches people to live jobs, runs AI interview practice, and connects candidates with real interviewers. This is the order it was built in, and why.

01

The idea: one resume doesn't fit every job

Most people write one resume and send it everywhere. But every role is read differently. A recruiter skims for a handful of signals, and the applicant-tracking system in front of them looks for the words in the job description. A good engineer applying for a data role with a resume written for a backend role loses before anyone reads it.

Tailoring fixes that: reorder what matters, use the posting's language for things you actually did, and cut what doesn't help. It works, but doing it by hand for every application takes an evening. The bet behind VettaCV was that a language model could do the first 80% in seconds, without inventing anything.

The rule from day one: tailoring may rephrase, reorder and emphasise. It never adds experience, tools or numbers the candidate didn't have. Everything later, from prompts to the diff view, was built around that.

03

Prototype: prove it in Streamlit first

The first version was a Streamlit page: upload a resume, paste a job description, get a tailored version back. Streamlit was the right call because it answered the only question that mattered: is the output good enough that someone would use it instead of editing by hand? No auth, no database, no design.

It was. The output problems showed up immediately though: the model returned prose when we needed sections, dropped bullet points, and occasionally "improved" a resume with skills the person didn't have. Fixing those, not the UI, became the real work.

From there it became CVSwitch, a Flutter web app where users could sign in, upload a resume and a job description, pick a template and generate a tailored CV. Behind it sat the first real API.

04

Getting structured data out of an LLM

A resume isn't text, it's data: contact details, jobs with dates, bullets, education, skills. Every feature needs that structure: the editor, the PDF, tailoring, matching. Early on we asked the model for JSON in the prompt and then validated it (the repo still has the commits named addvalidator and fixed validator). It mostly worked, and "mostly" is a bug factory.

Then OpenAI shipped Structured Outputs: you pass a Pydantic model, and the response is guaranteed to match it. We moved parsing onto it, and one schema became the backbone of the whole product: 

# abridged from the real schema
class WorkExperience(BaseModel):
    name: Optional[str]          # company
    position: Optional[str]
    startDate: Optional[str]
    endDate: Optional[str]
    description: Optional[str]

class Resume(BaseModel):
    basics: Optional[BasicInfo]
    workExperiences: Optional[List[WorkExperience]]
    education: Optional[List[Education]]
    projects: Optional[List[Project]]
    skills: Optional[Section]

# parsing, tailoring and the editor all speak "Resume"
completion = client.responses.parse(
    model=MODEL, input=messages, text_format=Resume)
resume = completion.output_parsed

The same shape is what the editor edits, what the PDF renders, what tailoring rewrites, and what job matching reads. No glue code between features, and no "the model forgot the closing brace" errors.

05

Spending fewer tokens

On a side-project budget every call matters, and cost scales with users. Most of the savings didn't come from clever prompts. They came from not calling the model at all when code could do the job.

Let the schema do the talking

With structured output, the prompt no longer carries long JSON examples and formatting rules. The schema is the instruction.

Send a compact resume

Prompts get a trimmed, plain-text version of the resume (sections and bullets, no layout or empty fields) instead of the raw document.

Right-size the model

Everything runs on small models (gpt-4o-mini, o4-mini, gpt-4.1-mini). Resume parsing even moved off a reasoning model (o4-mini) to gpt-4o-mini: no hidden reasoning tokens, and faster.

Regex before LLM

Importing a job from a link, reading pay ranges, detecting a candidate's country, and filtering jobs are plain code. No tokens, no latency, no surprises.

Cache and share

A company interview guide is researched once per company and role family and shared for 30 days: about $0.03–0.06 per guide instead of per user.

Charge only on success

Credits are deducted after a generation succeeds, so a failed call never costs the user, and retries don't double-charge.

06

Backend

PythonFlaskOpenAIFirebase AdminnginxEC2systemd

The API is a single Flask service. That was deliberate: one deployable, one place to read logs, one process to restart. It parses resumes, tailors them, writes cover letters, runs interview practice, matches jobs, and handles the interviewer marketplace.

Running lean

It runs on a small EC2 instance with about 1 GB of RAM. That constraint shaped a lot: heavy work like refreshing the jobs index runs as a separate, memory-capped job at 3 AM IST, never inside the web workers, and scheduled jobs never "catch up" after a restart, so a reboot can't trigger a memory spike.

Things that had to be right

  • Identity: every request carries a Firebase ID token, and the API checks it matches the user it acts on.
  • Money: credit grants are idempotent per payment ID and can only come from the server, never from the browser.
  • Email: interviewer notifications are batched (at most one an hour, two a day), with one-click unsubscribe.

Front-end: the editor, vibe coding, and the revert button

Next.jsReactTypeScriptTailwindFirebase Auth

The editor was the hardest part

People don't trust a resume they can't edit. The editor has to show exactly what the PDF will look like, update as you type, survive a refresh, and print pixel-perfect on A4 and Letter. We studied open-source JSON-driven resume builders, but none fit a flow where an AI rewrites sections and the user accepts or rejects each change. The first version took weeks, and the one that finally felt solid shipped in March 2026: drafts autosave locally, and printing comes straight from the rendered page.

Vibe coding, and why we got good at reverting

AI coding tools made it possible for a tiny team to ship a lot of UI quickly. They also made it easy to change ten files when you meant to change one. What kept it sane:

  • Small branches and pull requests, one change each, so a bad change is one revert, not an archaeology dig.
  • Preview pages with fixture data to check a screen in every state without logging in.
  • Type checks and tests before every merge, because "it compiled on my machine" isn't a release process.
  • Reading every diff. Generated code is a first draft, not a decision.

Design, take three

The look changed twice. A playful, mascot-heavy theme tested well for first impressions but felt like a toy for something as serious as a job search. The current design is calmer: neutral surfaces, one accent colour, lists instead of card grids, and Momo the Shiba kept for the moments that need warmth, like interview practice.

08

Choosing a database, and shaping the data

We chose Firebase: Auth for Google sign-in, Firestore for data, Storage for files. For a small team the deciding factors were sign-in out of the box, no servers to run, and a document model that fits a resume, which is one nested JSON object that kept changing shape as features grew.

How we think about the data

  • Everything hangs off the Firebase user ID. Resumes, saved jobs, filters, applications and credits are keyed by it.
  • A resume is one document, stored in the same shape as the Resume schema, so nothing translates between storage, API and UI.
  • Snapshots, not joins. When a candidate requests a mock interview we copy what the interviewer needs (years of experience, past companies, title) into the request, never their name or email. Privacy is decided when data is written.
  • Caches are just collections. Job-fit scores, company guides and embeddings are stored with a version stamp, so a model or prompt change invalidates them cleanly.
The trade-off: Firestore's queries are simple, so some filtering (location, salary, posted-within) happens in memory on a cached index. At hundreds of users that's faster and cheaper than adding a second database.
09

SEO, and now AEO

The marketing site is a statically exported Next.js site served from S3 and CloudFront: fast, cheap, and easy for crawlers. The SEO work came in rounds:

  • Fixing the basics: a robots.txt that accidentally blocked crawling, canonical URLs, redirects and breadcrumb schema.
  • A blog with practical guides (ATS checks, how to tailor a resume).
  • Programmatic pages like /resume-tips/[jobTitle], generated from a template for each common role.
  • Writing for answer engines too: clear question-and-answer sections that AI assistants can quote.

That last one is paying off: "AI Assistant" is now the second-largest traffic source after direct visits, ahead of organic search.

10

Payments with Razorpay

Pricing is credit-based with monthly and annual plans. Razorpay handles both currencies: INR for India, USD for everyone else. The rules that matter:

  • The server decides the currency from the visitor's country (with the browser time zone as a fallback). The client never chooses its own price.
  • The plan and billing period are read back from the Razorpay order, not from the browser, when credits are granted.
  • Each payment can grant credits exactly once, so a retried webhook or a double click can't double-credit.
11

Domain, DNS and AWS

The domain is registered at GoDaddy, but DNS lives in AWS Route 53, which keeps every record next to the services they point at. Three subdomains, three jobs:

  • www is the static marketing site on S3 + CloudFront.
  • app is the Next.js product on AWS Amplify, rebuilt on every push to main.
  • api is Flask behind nginx with TLS on EC2. The app proxies to it, so the browser only ever talks to one origin.

Email took its own afternoon: SPF, DKIM and DMARC records in Route 53 so notifications from the domain land in the inbox, not in spam.

12

From a tool to a job-search platform

Users kept asking the same question after tailoring a resume: "OK, where do I send it?" The 2026 work answers that.

Jobs matched to your resume

A daily index of openings from public company job boards (Greenhouse, Lever, Ashby) at dozens of companies, across India, Singapore, UAE, the US, the UK and Canada, ranked against your resume.

Apply in three clicks

Auto-tailor for the role, review a word-level diff, and get an apply kit with drafted answers to the application's own questions.

AI interview practice

Role-specific mock interviews with feedback, plus company guides built from cited web research.

Real interviewers

LinkedIn-verified professionals run paid mock interviews and can refer strong candidates. Candidates pick the round (system design, product sense…) they want to practise.

What I'd tell myself in 2024

  • Prototype the hard part, not the app. Streamlit proved the output was worth building around. Everything else could wait.
  • Pick one data shape and protect it. The Pydantic Resume schema saved more time than any framework choice.
  • The cheapest token is the one you don't send. Code first, then the smallest model that does the job well.
  • Constraints are a design tool. A 1 GB server forced clean background jobs and caching that would have been needed anyway.
  • Ship small, revert fast. With AI writing a lot of the code, review and small pull requests are the real engineering.
  • Listen for the next question. "Where do I send this?" turned a resume tool into a job-search platform.
